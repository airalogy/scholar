# 管理员授权、离职交接与应急恢复

[English](../en/administrator-governance.md)

本手册适用于包含管理员治理迁移的版本。升级前先备份数据库和配置；必须使用配套镜像执行迁移。代码和测试完成不等于生产部署或现场恢复演练完成。

## 身份与权限边界

工号、人员档案和登录账户属于具体的人。管理员离职时，应给接任者自己的账户授权，再撤销离职者权限，**不能把离职者账号的工号改成接任者工号**。历史审核、提交记录和操作者身份不随交接改写。同一人确有工号变更时，应走人员标识维护及核验流程，不使用交接功能冒名替换。

| 操作 | 机构 owner / 平台管理员 | 普通机构 admin |
| --- | --- | --- |
| 维护普通 member 的成员权限及邀请 | 可以 | 可以 |
| 授予、降级、移除 owner / admin | 可以 | 不可以 |
| 权限审计、管理员交接 | 可以 | 不可以 |
| 人员标识、目录纠错、审核授权及规则维护 | 可以 | 不可以 |
| 组织结构导入（涉及人员停用和实验室 owner） | 可以 | 不可以 |

审核资格仍需明确的、有效的审核授权；owner、admin、目录中的职务或导师关系本身不等于拥有最终审核资格。新授权对象必须通过当前人员状态和准入校验，不能依靠临时准入例外给已离职者重新授予权限。

建议保留至少两位独立核验、可正常登录的 owner。普通成员维护接口会阻止删除或降级最后一位有效 owner，并对并发变更重新检查。**权威目录确认离职、手动停用人员不会为了保留 owner 而放行离职账号**；即使因此没有可用 owner，也应走应急恢复。

## 日常授权与审计

在机构成员管理页选择真实目标账户，填写变更原因或工单编号，再授予或撤销角色。页面不允许普通 admin 管理其他管理员。服务端也会在事务内重新核验当前权限，旧页面、旧令牌或并发请求不能维持已经撤销的管理资格。

“管理员生命周期”面板提供有效 owner 数量、权限审计和交接。审计每页最多 50 条，保存操作人 ID 与姓名快照、来源、原因、变更前后值及时间，覆盖机构和实验室角色、邀请、审核授权、人员停用、接口凭证及平台权限变更。

- 页面变更和交接必须填写原因；为兼容旧客户端，旧成员/邀请接口未传原因时使用明确的默认来源说明。需要工单级追踪的调用方应始终传入 `reason`。
- 数据库触发器与权限修改处于同一事务，失败时一起回滚；拒绝审计表的更新、删除和清空。
- 不记录密码、密码散列、邀请令牌或 API 密钥。没有应用操作上下文的直接数据库操作会标记为 `database` / 未归属操作，需结合数据库访问日志追查。
- 迁移不伪造历史审计。该表是应用内只追加记录，不是能抵御数据库超级管理员的外部防篡改存储；备份、数据库权限隔离和必要的外部日志归档仍由运维负责。

## 计划离职：先预览，再交接

1. 接任者先用自己的身份完成登录、工号绑定和机构成员登记；核对在职状态与准入条件。准备另一位 owner，避免自交接后无法继续维护。
2. 检查离职者的平台权限。如果仍是平台管理员，先由有权限的服务器运维人员使用下述 `revoke-platform` 操作撤销，再进行机构交接。平台权限不会通过机构页面转让。
3. 在成员管理页选择离职管理员和接任者，点击“预览交接”。核对实验室所有权、审核授权、待办审核、待激活邀请及接口凭证数量。
4. **提前准备替代接口凭证**，包括离职者创建的目录同步凭证。交接会撤销其在本机构创建的全部未撤销凭证；同步服务可能需要重新配置。
5. 填写原因、确认待办清单，再执行交接。预览之后权限或待办发生变化会要求重新预览，不会按过时清单继续。
6. 交接在一个事务内完成：接任者获得相应机构角色（已有 owner 不降级）和实验室所有权；离职者被手动停用，机构/实验室管理权限和审核授权被撤销，待激活邀请被禁用，凭证被撤销。旧登录令牌后续访问会被拒绝。
7. 在审核治理中逐项处理待办：独立核验接任者审核资格，按需要另行授权和显式改派。交接**不会复制审核资格，也不会改写已完成审核、历史姓名或原始提交人**。用接任者账户验证权限，并复查审计。

网络中断时先刷新当前权限和审计，确认交接是否已完成；不要把超时当成未执行而盲目重试。

如果目录已先将离职者停用、降级，不能再把其当作在任管理员交接。由另一位 owner 或应急账户分别任命新 owner、补齐实验室所有者、处理审核授权与待办、替换失效凭证；不要为交接恢复离职者准入。重新入职也不会自动恢复旧管理权限和已撤销审核资格。

## 锁定后的服务器应急恢复

`bootstrap` 仅用于首次初始化新机构和新账户。已初始化机构即使所有成员被删除，也拒绝再次 bootstrap；它不再是恢复 owner 的捷径，也不会接管已有邮箱或用户名对应的账户。

只有获授权、能够进入部署主机并访问该实例配置的运维人员才能执行：

```sh
deploy/scholarctl recover-admin
```

该命令要求交互终端，使用与安装、升级、备份相同的操作锁；显示 `.env` 中的机构标识，要求填写操作人/事件编号、原因以及精确的 `RECOVER <机构标识>` 确认语句。恢复脚本还会校验输入机构与容器 `INSTITUTION_SLUG` 一致。它没有匿名 HTTP 恢复入口。

- `create`：创建一个全新、独立、**4 小时有效**的平台应急账户。用户名 3–64 字符，密码至少 12 字符且最多 72 个 UTF-8 字节；密码隐藏输入，通过标准输入传给容器，不放入命令参数或环境变量。不得复用离职人员账户，也不会重置已有账号密码。
- `revoke-platform`：输入精确用户 UUID，撤销其平台权限。对于临时恢复账户，同时立即终止其访问有效期；对于普通平台管理员，只撤销平台权限，机构权限仍需分别检查。

恢复流程：

1. 核对实例、版本、已执行的迁移、备份与事故记录；不要直接修改生产库角色或反复 bootstrap。
2. 如 `ENABLE_PASSWORD_SIGNIN=false`，按部署配置变更流程暂时启用密码登录并让 API 配置生效。保持公开注册关闭，不关闭既有 SSO 校验。恢复账户不会绕过密码登录开关。
3. 执行 `create`，用新账户登录。该账户不绑定离职者档案，因此不会因离职者的目录准入状态被锁死。
4. 核验实际接任者身份，恢复至少两位正常 owner，处理实验室、待办审核和集成凭证，分别验证正常登录与管理能力。
5. 立即执行 `revoke-platform` 回收应急账户，确认其旧令牌已失效；若临时打开密码登录，恢复原设置并验证 SSO。不要等四小时自动到期才回收。
6. 复查 `host_recovery` 审计、权限变更及相关主机日志，记录原因、执行人和验收结果。

到期检查发生在服务端每次认证时，已签发的令牌也不能在有效期后继续使用。应急账户有平台级能力，不能作为日常共享管理员账号；人员口头声明不是获得主机恢复权限的依据。

## 维护验证

```sh
pnpm check
GOVERNANCE_TEST_DATABASE_URL=<独立测试数据库连接串> pnpm db:verify:governance
DATABASE_URL=<独立测试数据库连接串> pnpm db:verify:upgrade
```

数据库测试使用随机隔离 schema，验证并发撤权、越权拒绝、交接与审计原子性、离职后旧令牌拒绝、邀请激活重新授权校验、首次初始化防重用及恢复账户失效。迁移测试保留旧数据、旧审核历史及初始化标记。界面测试验证预览、确认、过期预览处理、错误显示与请求取消。不要在生产数据库上做故障注入或恢复演练。

上线验收还应在预发布环境实际演练主机交互恢复、容器镜像、真实 SSO/目录连接、登录配置切换、凭证替换和备份恢复；自动测试不替代这些现场验证。
