# Airalogy Scholar 发布流程

[English](../en/releasing.md) | 简体中文

Airalogy Scholar 作为一个完整产品发布，内部由独立运行的 Web、API、迁移任务和可选 PostgreSQL 服务组成。每次发布必须把这些组件绑定到同一个经过验证的产品版本和不可变镜像摘要。

## 日常更新与发布的边界

有写入权限的维护者在确认变更范围并获得提交、推送授权后，默认直接更新 `main`。不按功能大小或复杂度划分流程；外部贡献、明确要求的审查或需要协作者审查时使用 PR。此约定不授予任何新的仓库权限。

日常更新按以下顺序进行：

1. 核对远端 `main`，保留工作区已有修改，列明并确认本次文件范围。遇到冲突、检查失败或范围变化时先停下说明。
2. 开发时运行 `pnpm check:quick`，按需重新生成源码清单。获得授权后提交，pre-push 根据待推送的全部提交执行受影响模块检查；公共依赖、检查规则、新分支或未知范围自动升级为全量检查。仅允许快进推送，不得跳过 hook、强推或删除主分支。hook 要求工作区与待推送的 HEAD 一致；保留无关修改时应使用独立工作目录，不要清除修改。
3. 等待并核对该提交对应的完整主分支 CI，包括代码、数据库、源码快照和 Docker 检查。不能使用旧提交的检查结果代替当前提交；如检查被后续推送取消，应验证新的目标提交。
4. 检查全部通过后，本次代码更新才算验证完成。升版本、创建标签、发布和部署仍需分别获得相应授权，部署前按现有流程完成备份。

仓库不再强制“先创建 PR”或“远端检查通过后才能写入 `main`”。完整 CI 保留为推送后检查，等待时可以继续开发；Release 可复用同一最终提交的可信完整 CI。因此主分支可能暂时包含尚未验证或检查失败的提交；待完成、失败、取消或结果未知的提交不得用于创建发布标签、发布或部署。仅取消 PR 要求不会自动取消原有检查前置限制，仓库设置须与本约定一致；这也不表示删除工作流或减少检查。

主分支继续要求线性历史，禁止强推和删除；发布标签继续禁止移动和删除。其他安全设置不因本约定放宽。选择 PR 时，仍须核对其完整检查并解决审查讨论后再合并。一次授权可以覆盖明确列出的连续步骤，但不包含未列明的动作；账号绑定、主工号、权限和数据变更仍须有明确授权及验证方案，推送代码不等于授权操作线上数据。

## 发布要求

- 使用干净的 `main` 提交，并确认该提交对应的完整 CI 已全部通过，不能仅依据它已进入主分支或其他提交的绿色结果。
- 每次提交使用 `git commit -s` 签署开发者原创声明（DCO）。
- 保持 `VERSION`、各包版本以及中英文 Changelog 一致。
- 审查数据库迁移、兼容性说明、存储要求和回滚条件。
- 不得把部署凭证、机构数据、私有地址或客户专属素材加入仓库或发布包。

## 验证发布源码

需要完整本地代码验证时运行（不包含真实 PostgreSQL 验证）：

```bash
pnpm install --frozen-lockfile
pnpm release:source:manifest
pnpm check
```

检查命令由 `scripts/run-checks.mjs` 统一管理并输出分组耗时；不使用可跨提交复用的本地“通过缓存”。本地快检保留配置、许可证、版本、文档和源码清单检查，并检查整个受影响模块，而不是猜测某几个测试；只改业务模块时不重复部署脚本测试。公共依赖、检查规则、部署脚本或未知文件变更仍走全量。全量 `pnpm check` 包含生产依赖审计、许可证、格式、lint、类型、全部非数据库测试、三个应用构建和 API 启动烟测。

远端 CI 将 quality、api、web、docs、database 五组并行放在干净源码快照中验证，保留空库、升级、身份绑定、审核权限和书目数据库回归，不再在原 checkout 中重复全量执行一次。`verify` 汇总每组结果，失败、取消或跳过任一必需组都不能通过。日常 Docker 检查只在容器配置、依赖等变更或无法识别范围时构建相关镜像；不再固定预热 ARM 镜像。正式发布始终保留两组件、两架构原生构建和烟测。本地快检通过不等于完整 CI 或正式发布通过。

如需从零验证，提供可丢弃的 PostgreSQL 测试数据库及其中的非 `public` schema。验证器会在测试库的 `public` 中初始化共享扩展，并删除、重建指定 schema，因此绝不能指向生产库或需要保留的数据。

```bash
RELEASE_SOURCE_DATABASE_URL='postgresql://.../scholar?schema=release_source' \
  pnpm release:source:verify
```

清单命令会原样保留已发布的初始迁移与全部增量迁移，扫描形似凭证的内容，校验 Changelog 基线，并在 `RELEASE-SOURCE-MANIFEST.json` 中记录文件的实际摘要。不得重新生成或替换已发布迁移。发布源码检查会在已提交清单与当前源码不一致时失败，包括迁移文件变动。

CI 同时验证空库和含已有机构身份、论文绑定的升级样例。需要单独运行升级验证时，设置 `DATABASE_URL` 后执行 `pnpm db:verify:upgrade`；它使用随机命名的 schema，并在同一连接中整体回滚样例和迁移。

## 创建发布

1. 在 `VERSION`、包元数据、`CHANGELOG.md` 和 `CHANGELOG.zh-CN.md` 中设置最终版本与日期。
2. 推送最终版本提交，等待并核对该提交对应的完整主分支 CI 全部通过，在干净提交上运行 `pnpm release:ci:check` 核对远端证据，再运行 `pnpm release:check` 核对本地版本、标签和工作区。版本提交有新 SHA，不能复用其父提交的结果。
3. 创建与 `VERSION` 完全一致的附注标签 `vX.Y.Z`。
4. 推送标签并等待 Release 工作流完成。

使用已登录的 GitHub CLI 查询已有运行：

```bash
gh run list --workflow release.yml --limit 5
pnpm ci:watch RUN_ID --repo airalogy/scholar --sha COMMIT
```

将 `RUN_ID` 替换为准确对应此次发布标签的运行编号，将 `COMMIT` 替换为完整提交 SHA。工具显示各组状态和耗时；提交不匹配返回未知，单个工作流成功不等于全部发布门禁通过。查询工具只读取状态，不会重启工作流或执行发布；默认每 15 秒查询一次，最多等待一小时。临时网络错误最多连续重试三次，逐次延长间隔；认证或权限错误不重试。可通过 `--interval SECONDS` 和 `--timeout SECONDS` 调整等待时间。退出码分别表示确认成功（`0`）、确认未成功，例如失败或取消（`1`）、因查询错误或超时而无法确认结果（`2`）。遇到 `2` 应重新查询同一运行或查看 GitHub 页面，不要认定发布失败或重新推送标签。

该工作流会：

- 重新检查生产依赖安全公告，并核对同仓库、同一最终 SHA、main/push 的最新 CI 运行及其最新尝试，要求全部必需任务成功；缺少记录时执行完整干净源码验证，失败、取消、跳过必需任务或查询结果未知时阻断，绝不找旧绿色结果替代；
- 构建 `linux/amd64` 和 `linux/arm64` 的 API 与 Web 镜像；
- 为每个镜像发布 SBOM 和构建来源证明；
- 在发布清单中记录不可变镜像摘要；
- 对准确的发布版 Compose 配置执行烟测；
- 发布部署归档、校验和与机器可读清单。

镜像缓存使用按组件和架构区分的独立 registry 引用，可跨版本复用；PR 不写入这些可信缓存。API 编译缓存与提交、标签、时间戳分开，最终镜像仍写入真实版本信息。缓存上传失败不影响验证结果，但任何构建或烟测失败都会阻断发布。生产升级脚本、停写、备份、健康检查和恢复边界不变。

发布标签不可移动。如果已发布版本存在缺陷，应在 `main` 修复后发布新的补丁版本，不得移动或复用原标签。

## 发布后验证

- 确认 GitHub Release 已发布，且包含部署归档、校验和、JSON 清单和环境变量清单。
- 确认 `ghcr.io/airalogy/scholar-api:X.Y.Z` 与 `ghcr.io/airalogy/scholar-web:X.Y.Z` 可公开拉取并与记录摘要一致。
- 在空环境安装发布版本，验证 `/healthz`、`/api/version`、`/docs/en/`、`/docs/zh/` 和 `/api/docs/json`。
- 保持 `main` 的完整推送后 CI、线性历史及禁止强推和删除的规则；PR 不再是维护者日常更新的强制入口。发布标签仍不可移动或删除。
- 保持 Dependabot alerts、secret scanning、push protection 和 private vulnerability reporting 开启。
